## 已确认的目标

一个中文 Web 面板完成 Compose 容器管理、升级、完整备份恢复、AI 排障和应用快捷入口。优先飞牛单机，保留现有相对路径 bind mount；用户不需要操作第二个备份面板。

“完整”按应用恢复能力定义，不包括飞牛操作系统整机镜像：

1. Compose 主文件、覆盖文件、环境文件、配置及应用所需密钥。
2. 项目内外的宿主挂载目录、单文件和 Docker 卷；保存所有者、权限、链接等必要元数据。
3. 数据库的一致性数据；首版优先受控停写，在线备份逐库适配，不能将热拷贝数据目录标记为一致性备份。
4. 精确镜像及自建镜像的离线导出；容器可写层变更必须检查并明确处理，不能静默丢弃。
5. 端口、网络、挂载、依赖与镜像清单；恢复时可映射到新目录和新卷。
6. 面板自身数据库、加密密钥的独立恢复流程；运行依赖如 Docker socket、设备和 tmpfs 在恢复时重建。

## 当前实现：运维执行与范围预检

新增的“运维”入口提供完整备份执行、升级前完整备份、宿主保存目录、任务记录，以及 115 官方直连和 WebDAV 的备份产物推送。执行条件、明确阻止的范围、密钥保管和隔离解密命令见[完整备份操作说明](FULL_BACKUP_OPERATIONS.md)。完整恢复 UI 尚未实现，真实恢复演练与代码测试须分别验收。

以下原有“存储清理”预检 API 保持只读语义：

入口：**存储清理 → 备份 → 完整备份范围预检**。

`GET /api/v1/ops/storage/full-backup-plan?projectId=<项目ID>` 使用现有会话鉴权，仅允许已纳管项目。请求读取固定节点的 Docker 清单与 inspect；按 Compose 项目名和工作目录双重匹配，防止同名项目串入。节点切换后拒绝旧清单。

响应列出 Compose、环境文件引用、配置与 secret 文件引用、声明挂载、实际 bind mount、实际卷、镜像 ID、可写层与运行依赖。响应不返回 Compose 内容、环境变量值或节点凭据。

预检对不可读文件、无法检查的容器、未展开的 include/extends、变量挂载、外部配置、共享写入源和过宽目录给出缺项提示。未部署的服务和运行中的容器另作提醒。

边界：

- **此预检 API 不执行备份或恢复**，不会创建 helper、停启容器、导出镜像或写入备份文件。新“运维”执行入口使用独立预检与确认令牌。
- 只有本机同路径可访问且已开启 Compose 目录访问的配置文件才会读取；SSH/TCP 节点不会错误读取本机同名文件。
- 原始 YAML 的引用收集不替代 `docker compose config` 最终模型解析。挂载源存在性、权限、大小、符号链接、卷驱动和排除项仍待宿主侧验证。
- 清单指纹用于比较预检内容，不是授权令牌，也不替代执行前重新读取和锁定范围。
- 原有命名卷备份保持原行为，不能据此声称完成了项目级备份。

## 后续实现顺序与验收

| 阶段 | 必须完成 | 通过标准 |
| --- | --- | --- |
| 1 范围预检 | 当前中文清单、阻断项与只读 API | 单测覆盖漏项、节点切换、同名项目与秘密不回显 |
| 2 完整备份 | 宿主侧路径检查、最终 Compose 模型、项目操作锁、停写与异常恢复、加密仓库、镜像导出、清单持久化 | 任一必备源失败不能标记成功；备份目标不能递归包含自身；中断后明确恢复原运行状态 |
| 3 完整恢复 | 清单和校验验证、解密、路径/卷映射、冲突检查、权限恢复、原版本重建 | 首先在新目录新卷恢复；不默认覆盖原应用；不要求源镜像仓库仍然可用 |
| 4 恢复演练 | 隔离网络/端口、数据库与应用检查、后台任务进度、失败记录 | 飞牛 Linux Docker 实际往返恢复通过，验证配置、附件、数据库记录与访问入口 |
| 5 日常闭环 | 定时备份、保留策略、异机存储、升级前备份、失败通知、自定义快捷地址 | 中文面板内完成操作；AI 查询预检和任务结果，恢复/覆盖仍走独立明确确认 |

本次采用 GNU tar、Docker 原镜像/commit 镜像和逐文件 AES-256-GCM 加密归档；不是去重仓库。后续引入 restic 等仓库时需兼容现有清单、外置密钥和隔离恢复验证，不以更换引擎为由缩减完整范围。
